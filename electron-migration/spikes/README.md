# Phase 0 gate spikes — results log

Per the migration plan (`pm-request/electron-python-migration-plan-2026-08-22.md` §8), all
five spikes must run before any port work. Results below; updated as each completes.

## S1 — better-sqlite3-multiple-ciphers DB compatibility — **PASS**

Ran 2026-08-22. Fixtures generated by the **real shipped Rust app's** own
`create_room`/`add_memory`/`rekey` code path (`src-tauri/examples/gen_fixture_room.rs`,
`cargo run --example gen_fixture_room -- <dir>`), not a hand-rolled approximation.
Verified by `s1-db-compat/s1_spike.mjs` against `better-sqlite3-multiple-ciphers` in Node:

- Opens a plain Rust-created room (`PRAGMA cipher='sqlcipher'; PRAGMA legacy=4; PRAGMA key=...`)
- `meta.format='roomai'`, `user_version=3` read back correctly
- Hebrew text round-trips as UTF-8 (no mojibake at the SQLite layer)
- Wrong password fails cleanly (no silent success)
- Single-quote-containing password opens correctly (confirms the `''`-doubling escape,
  since pragma has no parameter binding)
- A room rekeyed by Rust (`PRAGMA rekey`) opens with the new password only, old password fails
- **Reverse direction**: Node opens a Rust-created room, rekeys it via `PRAGMA rekey`, then
  the **original Rust app** (`cargo run --example verify_fixture_room`, using the production
  `open_room_readonly` path) opens the Node-rekeyed file successfully and reads its rows.

Conclusion: **zero-migration, bidirectional compatibility confirmed.** D2 stands as specced.
The pysqlcipher3-converter fallback is not needed. Both example binaries are kept in-repo
(not deleted) — plan §9 wants "a fixture `.room` created by the shipped Rust app opened by
CI forever"; these two examples are that harness.

## S3 — pywhispercpp Metal wheel — **PASS** — see `s3-metal-wheel/README.md`

Real result on this machine (Apple M4): Metal device found, embedded metal library loads via
plain Command Line Tools (no full Xcode needed — corrects an assumption in the plan), 60s-clip
bench matches the Rust harness's own methodology exactly. **Python/pywhispercpp came out
FASTER than today's Rust/whisper-rs**: 28.5x realtime vs 6.8x (likely a newer vendored
ggml/whisper.cpp — flash-attn, residency sets, graph fusion — that whisper-rs 0.16 doesn't
have yet). One real packaging gotcha found and fixed: the built extension's `LC_RPATH` points
at the ephemeral pip build temp dir, not `@loader_path` — must run `delocate-wheel` (or
equivalent `install_name_tool` repair) as part of vendoring the wheel, or it dlopen-fails the
moment the temp dir is gone.

## S2 — Touch ID keychain survival — **PARTIALLY VERIFIED; the hard part still needs the owner**

`electron/main/keychain.ts` now exists (koffi FFI to Security.framework/CoreFoundation, plus
the safeStorage fallback) and its non-biometric path is genuinely proven against the real
Keychain on this machine: add/find/delete of a real generic-password item round-trips
correctly (byte-exact UTF-8, including multi-byte characters), cross-checked with the
`security` CLI as an independent OS process at every step, and no test-created item is ever
left behind (verified: `security find-generic-password -s ArcelleKeychainPortTest` → not
found after the suite runs).

**What's still blocked**: the actual biometryCurrentSet / data-protection-keychain path — the
one this spike exists to answer — fails with `errSecMissingEntitlement` (-34018) in this dev
sandbox, because the data-protection keychain's access group derives from the code-signing
Team ID, which an ad-hoc-signed, no-Team-ID process doesn't have. This is expected and doesn't
tell us anything new; it's exactly why this spike needs (a) a Mac with a real enrolled Touch ID
room today, (b) the actual release signing scheme (Developer ID vs ad-hoc, Q2), and (c) a
physical Touch ID prompt. The code path is ready — `keychain.ts`'s `has()`/`store()`/`read()`/
`deleteEntry()` — for the owner to run against a real enrolled Mac once a properly signed build
exists; this line will be updated with that real result.

## S4 — loopback system-audio capture — **needs a human click for the TCC grant**

macOS here is 26.5.1, Electron target is 43.4.1 (plan said "≥39" — using current stable) —
both comfortably satisfy the `getDisplayMedia` loopback-audio requirement. Screen & System
Audio Recording is a one-time TCC grant that only a human clicking "Allow" in System Settings
can produce; nothing here can script that dialog. The renderer-side loopback lane gets built
during Phase 1's `rec/engine.py` + WS wiring step; **owner action needed** once that harness
exists: run the app, grant the permission when prompted, confirm a non-silent audio track.
